# Home-Automation-SoC — Stage Completion Governance

Effective: 2026-11-15
Applies to: all 19 tapeout stages.

---

## 1. Purpose

Prevent the failure mode this project already exhibits: reports and experiments accumulating while the design remains unmanufacturable. A stage is a **contract**, not a work log.

---

## 2. Mandatory stage process

Every stage follows these 12 steps, in order:

1. **Entry criteria** recorded and evidenced.
2. **Existing implementation inspected** (not assumed).
3. **Missing requirements identified** against the approved specification.
4. **Complete stage plan written**, including verification and audit tasks.
5. **Implementation performed** and recorded with artifact hashes.
6. **Verification run** on the current revision.
7. **Failures fixed** at the cause; no test weakening.
8. **Regression re-run** after every fix.
9. **Independent audit performed** by someone who did not implement the stage.
10. **Evidence frozen** (hash, tool version, command, log).
11. **Tracker updated** with criteria counts and evidence IDs.
12. **COMPLETE assigned** only after acceptance sign-off.

Skipping a step makes the stage `READY FOR AUDIT` at best, never `COMPLETE`.

---

## 3. Status definitions

| Status | Meaning | Allowed next action |
|---|---|---|
| NOT STARTED | no work or entry criteria unmet | start when entry criteria met |
| IN PROGRESS | implementation underway, incomplete criteria | continue; no downstream dependency may assume output |
| BLOCKED | dependency or decision prevents progress | resolve blocker or work a parallel non-dependent item |
| VERIFICATION FAILED | checks ran and failed | fix cause, re-run, re-audit |
| READY FOR AUDIT | implementation and verification complete, audit pending | independent audit only |
| COMPLETE | all criteria met, audited, evidence frozen | downstream stages may start |

A stage with a P0 blocker can never be `COMPLETE`. A stage with an open P1 blocker can be `COMPLETE` only with an approved, recorded waiver.

---

## 4. Completion prohibitions

A stage **must not** be marked COMPLETE if any of the following is true:

- required implementation is missing or stubbed;
- a mandatory test has not run on the current revision;
- verification failed or was skipped;
- a critical blocker remains;
- evidence is missing, stale, or not reproducible;
- the independent audit has not passed;
- the result depends on an experiment outside the production baseline;
- the report exists but the artifact does not.

**Documentation is not implementation. A tool invocation is not acceptance. A block-level result is not full-chip evidence.**

---

## 5. Evidence acceptance rules

1. Every acceptance criterion cites an `EV-*` ID in `TAPEOUT_EVIDENCE_REGISTRY.md`.
2. Evidence carries: artifact path, SHA-256, tool and version, design revision, command, result, limitations.
3. Logs must be generated by the run they describe; a marker in a summary without its log is invalid (see BLK-010).
4. Hashes are computed after the run is frozen; regenerated logs are re-hashed.
5. Stale or contradictory evidence is retained and marked, never overwritten.
6. Screenshots and prose may support, never replace, machine-checkable evidence.
7. Experiment results (`experiments/**`) are `EXPERIMENTAL` and cannot satisfy a stage gate unless the stage explicitly permits experiments (none do).

---

## 6. Independent audit

- The auditor must not be the implementer of the stage under review.
- The audit samples artifacts, re-runs at least one check, and verifies hashes.
- The audit report lists findings with severity and either closure evidence or a waiver.
- An audit with unresolved High findings fails the gate.

Recorded audits so far:
- Phase 4.21 gate prototype — 9/9 regression, prototype status.
- Phase 4.22 gate — independent audit found 4 defects (unknown clock master, missing-master drop, hardcoded geometry, no hash binding); fixed in the experiment copy; 24/24 regression.
- Stage 0 — this baseline audit.

## 7. Roles

| Role | Responsibility | Current assignment |
|---|---|---|
| Program owner | stage authorization, waivers, final release | **unassigned** |
| SoC architect / design owner | architecture, clock/reset/power, SDC approval | **unassigned** |
| RTL lead | RTL closure and review | **unassigned** |
| Verification lead | functional/formal/CDC evidence | **unassigned** |
| PD lead | synthesis, constraints, physical, signoff | **unassigned** |
| DFT lead | scan/ATPG/BIST | **unassigned** |
| Independent auditor | gate audit | rotating, must not be implementer |

Unowned roles are themselves a P1 program blocker: no decision can be approved without an owner. This must be resolved before Stage 1 can complete.

---

## 8. Waivers

A waiver is valid only if it states:

- check and artifact;
- exact violation (value, limit, location);
- technical justification;
- risk and downstream impact;
- owner and approver;
- expiry stage or date;
- compensating evidence.

Blanket waivers ("known issue", "acceptable for now") are invalid.

Current candidate waivers (not approved):
- 1 antenna violation on the timer block after DRT (Phase 4.22).
- `debug_jtag` 0-cell synthesis result pending explanation.
- `spi_miso` unsynchronized input (argued same clock domain).

---

## 9. Change control and baseline freeze

- Frozen artifacts: RTL filelist hash, netlist, SDC, DEF, SPEF, GDS.
- Any change to a frozen artifact re-opens its stage and all dependents.
- Experiments may branch from a frozen baseline but never modify it.
- Production flow scripts and constraints are read-only until their stage is active and the change is approved.

---

---

## 11. Review cadence

- Tracker reviewed at the start and end of every working session.
- Stage status changes require an evidence reference in the same edit.
- Any new experiment must be linked to a stage and classified EXPERIMENTAL.
- Contradictions found in documents are recorded in the Stage 0 audit or the decision register; they are not silently edited away.

---

## 12. Enforcement

The Stage 0 audit found multiple green claims that were not reproducible (stale 25/25 summary, `TEST_RESULTS.md` 8 PASS/4 BLOCKED vs 22/22, "13 blocks synthesize" while full SoC does not). Under this governance:

- those claims are reclassified, not deleted;
- the next agent must re-run a check before relying on it;
- a stage cannot inherit a green status from a previous report without re-verification.
